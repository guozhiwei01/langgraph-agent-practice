要素一

意图识别：这封邮件想干什么？

先判断客户问什么？是常规问题，还是退款、安全、人工请求等需要谨慎处理的情况？
邮件→意图 / 风险→常规流程 or 人工

TypeSafe 给出结构化分类；代码根据置信度和风险决定走哪条路。识别不可靠时，不硬猜，直接交人。

它负责什么理解用户目标、主题、紧急程度、复杂度和风险。
它不负责什么不负责检索全部资料，也不负责发送邮件。
典型输入 / 输出输入邮件正文；输出 intent、confidence、needs_human 和风险分数。
连接另外两要素输出决定工作流走哪条路径，也决定边界是否提前介入。
只记一句：先分流，再处理。分类是路由依据，不是发邮件的许可。

要素二

工作流：接下来怎么走？

常规路径查资料 → 筛证据 → 写草稿 → 验证草稿 → 等人工审核。
检索→证据→草稿→验证

LangGraph 安排顺序和分支。证据不够就写澄清草稿，不编造答案；高风险邮件跳过这条自动草稿路径，直接交人工。

它负责什么把一次处理拆成可观察、可恢复、可分支的步骤。
它不负责什么不自己决定业务政策，也不因为模型说安全就自动越权。
典型输入 / 输出输入意图和当前 State；输出下一节点、草稿、证据和状态变化。
连接另外两要素读取意图识别结果来选路，并在边界设置的人工节点处暂停或结束。
只记一句：根据意图走不同路径，流程不是“一条直线跑到底”。

要素三

边界：在哪里必须停？

贯穿全程风险在分诊时就会改变路径，证据不足会收缩回答，模型写好草稿后也不能自行发送。
风险 / 证据 / 草稿→代码规则→人工授权→副作用

即使回复验证显示安全，也只能辅助人判断。调用 Gmail、创建 Bug Issue 等外部副作用，必须经过代码规则与人的授权。

它负责什么规定允许做什么、必须暂停什么、失败后能否继续。
它不负责什么不替代意图识别，也不编排每个普通步骤。
典型输入 / 输出输入风险、验证结果和人工决定；输出继续、拒绝、澄清或外部副作用。
连接另外两要素风险信号可让工作流提前停下；批准结果让工作流从暂停点继续。
只记一句：能判断 ≠ 有权执行；模型给信号，代码定规则，人类批副作用。

ELEMENT 1 / INTENT

要素一：意图识别

用户想做什么？当前有多大风险？

意图识别不是只给邮件贴一个标签，而是形成一份供工作流和边界共同使用的“局势判断”。它决定系统是否继续自动处理、选择哪类知识，以及是否需要立即交给人。

输入邮件正文、标题和当前上下文。
核心判断intent、urgency、complexity、置信度与三类风险。
输出classification 与 needs_human，交给工作流选路。
失败原则识别失败或不确定时 fail closed，直接转人工。
连接工作流普通问题继续检索；高风险问题跳到 human_review。
连接边界风险信号只触发限制，不授予任何外部执行权限。
ELEMENT 2 / WORKFLOW

要素二：工作流

系统怎样把事情一步步完成？

工作流把意图识别产生的方向变成业务步骤，并负责分支、状态传递、异常降级与人工中断。LangGraph 决定“下一步做什么”；Worker、Queue 和数据库属于让流程可靠运行的工程地基。

输入邮件原始信息、classification 和当前 Graph State。
常规路径检索 → 证据筛选 → 草稿 → 验证 → 人工审核。
分支高风险直达人工；证据不足生成澄清；拒绝后结束。
状态EmailAgentState 在节点之间传递输入、判断和结果。
编排边界Graph 管业务步骤，不负责进程调度、任务抢占或服务托管。
完成标准到达等待审核、发送成功或明确拒绝等可观察状态。
ELEMENT 3 / BOUNDARY

要素三：边界

系统最多能做到哪里？什么时候必须停？

边界把“有能力做”与“被允许做”分开。模型提供判断和草稿，Python 落实策略，人类授权真实副作用。幂等、审计和恢复机制负责在工程上维护这些边界，但不等于边界本身。

能力边界模型不能直接调用 Gmail、GitHub 或承诺退款。
信息边界证据不足不编造；提示注入和敏感信息触发限制。
授权边界human_review 暂停；批准、编辑或拒绝由人决定。
副作用边界发送与建 Issue 只在授权后发生，并使用幂等保护。
决策边界模型分数只是信号；阈值、降级和路由由 Python 策略落实。
失败原则不确定、证据不足或能力异常时收缩自动化，优先澄清或交人。
工作流展开：业务路径读取意图信号在边界节点暂停

图状态的职责

服务一次 LangGraph 执行，支持节点间数据传递和 interrupt 检查点。当前由 PostgresSaver 保存，应用重启后仍可恢复。

业务数据库的职责

支持 Web 列表、审核、队列、Outbox、审计、去重和发送投影。即使 Web 或 Worker 重启，待执行工作和用户可见状态仍然存在。

连接器：三道判断闸门分别服务于方向、质量和安全
CONNECTOR / DECISION GATES

贯穿流程的三道判断闸门

三次判断使用同一种结构化决策能力，但职责不同：分诊属于意图识别，证据门控服务工作流，回复验证守住边界。

DECISION 1 意图识别

邮件分诊

一次请求得到 intent、urgency、complexity，以及退款、安全事件、人工请求三个风险分数。

needs_human = other
∨ intent_confidence < 0.7
∨ complexity == specialist
∨ urgency == critical
∨ any_risk_score ≥ 0.7
→
DECISION 2 工作流质量

证据门控

每个 passage 判断 relevant、supports、injection；合格项按 0.4×相关性 + 0.6×支持度排序，最多取 3 条。

accepted = relevant ≥ .7
∧ supports ≥ .7
∧ injection < .7

sufficient = selected ≠ ∅
∧ answer_supported ≥ .7
→
DECISION 3 边界安全

回复验证

检查是否回答问题、是否有依据、是否越权承诺、是否索取敏感信息，以及总体质量。

safe = addresses ≥ .7
∧ grounded ≥ .7
∧ commitment ≤ .3
∧ sensitive ≤ .3
∧ quality ≥ 2
TypeSafe：信号层

输出概率、分数和结构化记录；不能发邮件、退款或建 Issue。

Python：策略层

阈值计算、路由、重试、降级、脱敏、幂等键和状态约束。

人类：授权层

当前任何回复都必须批准；Bug Issue 也只在批准动作后创建。

最重要的安全设计即使 safe_to_send=True，节点仍然无条件进入 human_review。安全评分目前是给审核员看的信号，不是自动发送开关。
连接器：端到端场景同时观察意图、流程、边界与工程地基

三个恢复层次

Job Queue 恢复“哪个工作要重做”；PostgresSaver 恢复“Graph 从哪个节点继续”；Outbox 恢复“外部发送是否已经发生”。三者缺一不可。

三类 PostgreSQL 事实

业务表保存用户可见状态；job_queue 保存执行状态；Checkpoint 表保存图内部状态。它们通过 task_id 和 langgraph_thread_id 建立关联。

仍要注意的三个实现边界
  1. Web 和 Worker 是两个进程：只启动 Web 会产生 queued Job，但不会真正处理；生产环境必须由进程管理器同时托管二者。
  2. 批准/拒绝首次恢复使用 Command(resume=...)；节点执行失败后的 Job 重试必须用 stream(None)，否则会重复提交 interrupt 决定。
  3. Outbox + RFC Message-ID 对账显著缩小 Gmail 重复窗口，但 Gmail 搜索索引延迟意味着它不是严格 exactly-once。

系统怎样被运行、观察和追责

生产化不是再加一个模型节点，而是让每次请求都有执行归属、重试边界、审计记录和可报警信号。

1 · ENQUEUEWeb 事务性写入 job_queue；审核与邮件处理使用稳定去重键，同步请求则保留独立执行记录。

退避公式

delay = min(900,
5 × 2^(attempt-1))

默认从 5 秒开始，单次最长 15 分钟。每类 Job 可以配置 max_attempts。

租约与回收

Worker 以 stale_seconds / 3 的频率刷新租约；每个 Worker 至少每 60 秒扫描过期 running Job 并放回 retry。

死信处理

dead 不会静默消失。任务型死信显示在邮件卡片；无 task 的同步死信独立显示，审核员可手动重放。

用三要素检验是否真正理解

先自己回答，再展开参考方向。能够定位到代码位置，比背流程更重要。

【连接器：证据闸门】为什么 evidence_sufficient=False 时不直接让 DeepSeek“尽量回答”？
因为检索结果只是候选，可能不相关、缺少支持或包含提示注入。项目选择进入 draft_clarification，用不确定性换取可控性。
【边界】safe_to_send=True 为什么仍然进入人工审核？
当前阶段把验证结果当作审核辅助信号，而不是授权。副作用权限仍由人工掌握，避免模型评分直接触发真实外发。
【意图识别 → 边界】如果 TypeSafe 服务在分诊时不可用，邮件会怎样？
triage_error_handler 构造低置信度、specialist、needs_human=True 的分类记录，并直接进入 human_review，属于 fail closed。
【工程地基】PostgresSaver 和 agent_tasks 表分别保存什么？
PostgresSaver 保存 LangGraph 的完整 checkpoint、暂停节点和 channel writes；agent_tasks 保存 Web 列表需要的任务状态、草稿和决策投影。业务表不是 Graph checkpoint 的替代品。
【工程地基 → 边界】Gmail 发送的重复风险现在怎样被缩小？
send_reply 节点先写 Outbox，固定正文、幂等键和 RFC Message-ID。重试时若 Outbox 未完成，会先用 Message-ID 搜索 Gmail 已发送邮件：找到则补齐本地状态，找不到才发送。残余风险来自 Gmail 搜索索引的最终一致性。
【工作流 → 工程地基】为什么 Job 重试不能总是再次发送 Command(resume=...)？
Command(resume) 只适用于 checkpoint 正停在 human_review interrupt 的第一次恢复。如果 send_reply 已经开始但失败，checkpoint 的 next 是 send_reply；此时应使用 stream(None) 从失败节点继续，否则会错误地重复提交人工决定。
【工程地基】job_queue 与 PostgresSaver 分别解决什么问题？
job_queue 决定某项工作何时由哪个 Worker 执行，并提供退避、租约和死信；PostgresSaver 保存 Graph 内部 State、interrupt 和下一个节点。只有队列没有 checkpoint 会重跑整张图，只有 checkpoint 没有队列则无人可靠地触发恢复。
【工程地基】Worker 为什么总是尝试 enqueue process_email？
邮件入库与 Job 入队是两个事务。如果进程恰好在二者之间崩溃，下次同步会看到邮件已经存在。依靠 task:{id}:process 去重键，每次都尝试 enqueue 才能修复这个孤儿任务窗口。
