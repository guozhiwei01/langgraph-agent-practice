# 邮件 Agent 提示词：学习版与生产版的演进记录

本文记录 `src/email_agent/prompts.py` 中分类和回复草稿提示词的局限与后续改进方向。**这是设计备忘，不代表这些功能已经实现**；当前仍是学习骨架，源码提示词继续保持英文。本文件用中文解释设计，后续实现时再决定具体英文措辞。

相关的多问题数据建模与路由见 [邮件多意图分类与处理策略](intent-classification-and-routing.md)。

## 当前状态

- `CLASSIFICATION_PROMPT_TEMPLATE` 只要求给出 `intent`、`urgency`、`topic`、`summary`，未定义取值含义、紧急度标准或异常情形。
- `DRAFT_RESPONSE_TEMPLATE` 只要求礼貌、直接回应、参考文档，未规定资料不足、多问题、升级人工、实际操作状态及输出语言。
- 提示词本身不能代替图节点、结构化校验、文档检索、人工审批和工具调用；这些能力当前尚未因写下本文而具备。

## 第一阶段：学习分类与单问题回复

目标是把“分类 → 搜索资料 → 生成草稿 → 人工确认”跑通，保留现有单 `intent` 的 `EmailClassification`，不急于实现生产级多意图系统。

### 分类提示词的最小改进

1. 写明 `intent` 只能是 `question`、`bug`、`billing`、`feature`、`complex`，`urgency` 只能是 `low`、`medium`、`high`、`critical`；字段名和值与当前 `schemas.py` 一致。`feature` 在这里指功能请求，`complex` 暂作学习版的复杂问题兜底类。
2. 给每类意图简短定义和边界：咨询归 `question`，故障归 `bug`，扣费归 `billing`，新功能建议归 `feature`；例如 API 504 究竟归 `bug` 还是 `complex`，应明确优先规则，而不是留给模型猜。
3. 给紧急度可测试的例子：普通咨询通常 `low`；有替代办法的故障可为 `medium`；重复扣费或主要功能不可用通常至少 `high`；安全事件、数据丢失或大范围中断才考虑 `critical`。这些是学习用示例，不是未经业务确认的生产 SLA。
4. 明确现阶段只选一个主要意图，其他问题保留在 `summary`；不宣称这样就已经妥善处理了多问题邮件。
5. 用模型结构化输出配合 `EmailClassification`，再做运行时校验与失败处理；不要仅靠“请返回 JSON”这句话保证类型正确。

### 草稿生成提示词的最小改进

1. 明确回答应依据检索到的资料；资料不足、互相冲突或不相关时，不编造步骤、链接或产品能力，标记为需人工确认的草稿。
2. 要求逐项回应邮件中提到的问题。单意图路由只决定主要处理路径，不能成为忽略其他问题的理由；无法回答的部分要清楚说明仍待核实。
3. 默认使用客户邮件的语言，保持礼貌和同理心，并明确输出只包含邮件正文（如产品需要主题行，再单独定义结构）。
4. 不声称已退款、已修复、已创建工单、已安排回访或承诺完成时间，除非工作流确实获得了对应操作结果。草稿不等于发送成功。

学习阶段可以使用人工确认作为发送前的安全边界；这里的“标记待人工”只是草稿/状态建议，不意味着当前已有升级工具。给几类样例邮件做测试：密码重置、PDF 导出崩溃、重复扣费、深色模式请求、间歇性 API 504，以及资料为空和一封邮件含两个问题的情况。

## 第二阶段：实现草稿生成流程时

当检索节点、草稿节点和审核节点真正接入后，让提示词只承担它能承担的事，并由代码提供可靠上下文：

- 传入原始邮件、已校验的分类结果、检索资料及其来源、实际完成的工具操作；不要把“模型认为已经完成”当作操作凭据。
- 将邮件正文和检索内容明确标成**不可信数据**，与开发者指令分隔。邮件或资料中若出现“忽略之前要求”等文字，只按客户内容或资料内容处理，不能当成新指令。边界标记可以帮助模型理解，但不能替代工具权限和程序校验。
- 为资料设置来源、标题或链接，明确什么时候在回复中引用；资料无关、过期或相互冲突时走待核实/人工审核，而不是拼接出确定答案。
- 定义草稿输出结构与状态，例如正文、所依据的资料、未解决问题、是否需人工确认。由审核节点决定是否发送，发送动作和发送状态必须由工具反馈确认。
- 为失败路径写测试：结构化分类校验失败、无搜索命中、模型超时、工具失败、客户诱导越权、草稿漏答及未经执行却声称退款。

这一步仍可保留学习版单意图模型，但不能将它误认为已覆盖复杂邮件。是否接入真实邮箱、是否自动发送及允许哪些操作，需单独由业务规则决定。

## 第三阶段：生产环境的目标设计（以后实现）

### 分类与路由

- 从“整封邮件只有一个标签”演进为提取多个 `issue`：每个问题有自己的意图、主题、摘要、紧急度、重要性和处理状态；两个问题可以同为 `primary`。
- 将 `complex` 从业务意图中拆出，改为复杂度或升级理由；将 `feature` 明确为 `feature_request`。这是未来 Schema 变更，不是当前字段的解释性改名。
- 对每个 issue 分发处理，再汇总成**一封**完整回复；无法安全自动处理的 issue 单独升级，不能让一个分支的成功掩盖另一分支的失败。
- 紧急度不能只听模型判断：结合确定性的安全、资金、服务中断规则和人工复核；分类不确定或冲突时保留证据并升级。

### 回复与操作约束

- 草稿节点接收每个 issue 的处理结果、有效资料和实际操作回执，逐项区分“已解决”“待核实”“已转交”“待跟进”。
- 涉及退款、赔付、权限变更、合同、安全事件或敏感数据时，按授权规则和人工审批执行；提示词不能赋予模型操作权限。
- 跟进必须由调度/工单工具真正创建并返回确认，草稿才可陈述具体安排；绝不虚构工单号、完成时间或退款结果。
- 自动发送前校验覆盖率、依据、敏感信息、语言、事实性和审批状态；多分支结果冲突时阻止自动发送并交人工。

### 工程保障

- 邮件与文档都是潜在的提示词注入来源；结合最小工具权限、数据隔离、输出校验和人工审核防护，而非只靠一条“忽略恶意指令”的 Prompt。
- 对发件人邮箱及邮件正文中的个人信息做最小化使用、日志脱敏与权限控制。分类通常只需正文；如不需要身份信息，就不要把 `sender_email` 交给模型。
- 加入幂等、重试、超时、审计和可观测性，区分“草稿已生成”“人工已批准”“工具已执行”“邮件已发送”。
- 用真实但脱敏的多问题样例和对抗样例评估：分类正确率、问题覆盖率、引用可靠性、误承诺率、升级准确性和重复发送率。规则、阈值及 SLA 需要产品和客服团队确认。

## 不应混淆的边界

**学习版先跑通机制，生成阶段保证草稿有依据且可审核，生产版再追求完整的多问题处理与可靠交付。** 改进提示词只是其中一部分；Schema、图状态、工具、权限、持久化、审批和测试必须配套演进。当前只记录方案，不修改 `prompts.py` 或声明生产能力已落地。
