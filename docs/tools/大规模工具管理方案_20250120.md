**大模型如何调用 Python 函数？**

传统方式：
```python

```

AI Agent 方式：
```python

## 四、关键技术：参数拆分（解包）

### 4.1 什么是参数拆分？

**问题：** LLM 返回的是字典格式，函数需要的是多个参数

```python
# LLM 返回
{"a": 3, "b": 4}  # 字典（打包的）

# 函数需要
add(a=3, b=4)  # 多个参数
```

**解决方案：** 用 `**` 把字典拆分成多个参数

```python
args = {"a": 3, "b": 4}
add(**args)  # ** 拆分字典
# 等价于 add(a=3, b=4)
```

---

### 4.2 参数拆分的原理

#### Python 的 `**` 拆分
```python
def add(a, b):
    return a + b

# 字典
args = {"a": 3, "b": 4}

# 三种等价写法
add(**args)           # ✅ 拆分字典
add(**{"a": 3, "b": 4})  # ✅ 拆分字典
add(a=3, b=4)         # ✅ 直接传参
```

#### PHP 的 `...` 拆分
```php
function add($a, $b) {
    return $a + $b;
}

// 数组
$args = [3, 4];

// 两种等价写法
add(...$args);  // ✅ 拆分数组
add(3, 4);      // ✅ 直接传参
```

---

### 4.3 为什么必须拆分？

#### ❌ 不拆分（错误）
```python
def add(a, b):
    return a + b

args = {"a": 3, "b": 4}
add(args)  # ❌ 错误！
# TypeError: add() missing 1 required positional argument: 'b'
# 原因：传了 1 个参数（字典），但函数需要 2 个参数
```

#### ✅ 拆分（正确）
```python
add(**args)  # ✅ 正确！
# 拆分成：a=3, b=4
```

## 五、`invoke()` 的底层实现

### 5.1 简化版实现

```python
class SimpleTool:
    def __init__(self, func):
        self.func = func  # 保存原始函数
        self.name = func.__name__
    
    def invoke(self, args: dict):

## 八、Python 传统函数调用方式

### 8.1 核心原理：函数是对象

**Python 中，函数是"一等公民"（First-class Object）**

```python
def add(a, b):
    return a + b

# 函数可以赋值给变量
func = add  # func 和 add 指向同一个函数对象

# 通过变量调用
result = func(3, 4)  # 等价于 add(3, 4)

# 验证
print(func is add)  # True（同一个对象）
```

---

### 8.2 Python 传统调用的 5 种方式

#### **方式1：直接调用（最常见）**
```python
def add(a, b):
    return a + b

result = add(3, 4)  # 直接调用
```

#### **方式2：通过变量调用**
```python
func = add  # 函数赋值给变量
result = func(3, 4)  # 通过变量调用
```

#### **方式3：通过字典调用**
```python
# 函数放到字典里
functions = {
    "add": add,
    "multiply": multiply
}

# 动态调用
func_name = "add"
result = functions[func_name](3, 4)
```

#### **方式4：拆分列表**
```python
args = [3, 4]
result = add(*args)  # * 拆分列表
# 等价于 add(3, 4)
```

#### **方式5：拆分字典**
```python
kwargs = {"a": 3, "b": 4}
result = add(**kwargs)  # ** 拆分字典
# 等价于 add(a=3, b=4)
```

---

### 8.3 `invoke` 的本质：方式2 + 方式5

**`invoke` 就是「通过变量调用 + 拆分字典」的组合！**

```python
class Tool:
    def __init__(self, func):
        self.func = func  # ← 方式2：函数赋值给变量
    
    def invoke(self, args: dict):
        return self.func(**args)  # ← 方式2 + 方式5
        #      ^^^^^^^^^  ^^^^^^
        #      变量调用    拆分字典
```

**等价于：**
```python
# 传统方式
func = add  # 赋值给变量
result = func(**{"a": 3, "b": 4})  # 变量调用 + 拆分字典

# invoke 方式（本质一样）
tool = Tool(add)
result = tool.invoke({"a": 3, "b": 4})
```

---

### 8.4 验证：invoke 内部用的就是变量调用

```python
def add(a, b):
    return a + b

# 方式1：传统的变量调用
func = add
result1 = func(3, 4)
print(result1)  # 7

# 方式2：invoke（本质一样）
class Tool:
    def __init__(self, func):
        self.func = func  # 保存到变量
    
    def invoke(self, args):
        return self.func(**args)  # 通过变量调用

tool = Tool(add)
result2 = tool.invoke({"a": 3, "b": 4})
print(result2)  # 7

# 验证：是同一个函数对象
print(func is add)        # True
print(tool.func is add)   # True
```

### 8.5 为什么要用变量保存函数？

#### **场景1：动态选择函数**
```python
# 不用变量（硬编码）❌
if name == "add":
    result = add(3, 4)
elif name == "multiply":
    result = multiply(3, 4)
elif name == "divide":
    result = divide(3, 4)
# 每个函数都要写一遍，不通用

# 用变量（动态）✅
tools = {
    "add": add,
    "multiply": multiply,
    "divide": divide
}
func = tools[name]  # 通过变量拿到函数
result = func(3, 4)  # 通过变量调用，通用！
```

#### **场景2：保存函数供后续使用**
```python
class Tool:
    def __init__(self, func):
        self.func = func  # 保存到实例变量
    
    def invoke(self, args):
        return self.func(**args)  # 随时可以通过变量调用

# 创建时保存函数
tool = Tool(add)

# 以后随时可以调用
result1 = tool.invoke({"a": 3, "b": 4})
result2 = tool.invoke({"a": 10, "b": 20})
result3 = tool.invoke({"a": 100, "b": 200})
```

---

### 8.6 总结：invoke 的本质

```python
# invoke 本质上就是：
# 1. 把函数保存到变量（self.func = func）
# 2. 通过变量调用函数（self.func(**args)）

class Tool:
    def __init__(self, func):
        self.func = func  # ← 步骤1：保存到变量
    
    def invoke(self, args):
        return self.func(**args)  # ← 步骤2：变量调用 + 拆分
```

**对比表格：**

| 方式 | 代码 | 本质 |
|------|------|------|
| **直接调用** | `add(3, 4)` | 通过函数名 |
| **变量调用** | `func = add; func(3, 4)` | 通过变量 ✅ |
| **invoke** | `tool.func(**args)` | 通过变量 ✅ |

**核心：`invoke` = 变量调用 + 字典拆分**

## 十二、常见问题

### Q1: 为什么不直接 `add(args["a"], args["b"])`？

**A:** 可以，但有问题：

```python
# 方式1：手动提取（不通用）
def call_add(args):
    return add(args["a"], args["b"])

def call_multiply(args):
    return multiply(args["a"], args["b"])

# 每个函数都要单独处理！❌

# 方式2：用 ** 拆分（通用）
def call_any_tool(tool, args):
    return tool.invoke(args)  # 所有工具通用 ✅
```

### Q2: 拆分和匿名函数（lambda）有关系吗？

**A:** 没关系，是两个不同的概念：

```python
# ** 拆分：把字典变成参数
add(**{"a": 3, "b": 4})

# lambda：定义匿名函数
add_lambda = lambda a, b: a + b

# 可以结合使用
add_lambda(**{"a": 3, "b": 4})
```

### Q3: PHP 怎么实现？

**A:** 用 `...` 拆分（PHP 5.6+）

```php
// 索引数组
$args = [3, 4];
add(...$args);

// 关联数组（PHP 8.0+）
$args = ['a' => 3, 'b' => 4];
add(...$args);
```

### 核心原理

```
┌─────────────────────────────────────┐
│ LLM 只负责「决策」                    │
│ 生成 JSON 格式的调用指令              │
│ {"name": "add", "args": {...}}      │

              ↓
┌─────────────────────────────────────┐
│ 返回结果给 LLM                       │
│ ToolMessage(content=7)              │
└─────────────────────────────────────┘
```

### 关键技术点

1. **参数拆分（`**`）**: 把字典变成多个参数
2. **动态查找**: 通过名字找到函数
3. **通用调用**: 所有工具用同样方式

### 记忆口诀

```
LLM 生成指令（JSON）
  ↓
字典拆分成参数（**）
  ↓
传统方式调用函数
  ↓
返回结果给 LLM
```

### 15.5 完整架构实现

```python
from langchain.tools import PythonREPLTool
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, END
from typing import TypedDict, List

class State(TypedDict):
    messages: List[dict]
    generated_tools: str
    
# 持久化的 Python 环境
python_env = PythonREPLTool()
llm = ChatOpenAI(model="gpt-4")

def analyze_and_generate_tools(state: State) -> State:
    """分析需求，生成所需工具"""
    
    user_request = state["messages"][-1]["content"]
    
    prompt = f"""
用户需求：{user_request}

你是一个工具生成专家。分析这个需求需要什么工具，然后生成它们。

要求：
1. 生成完整、可运行的 Python 函数
2. 函数要有清晰的参数和返回值
3. 可以导入任何标准库
4. 只生成代码，不要解释

示例：
def calculate_fibonacci(n: int) -> int:
    if n <= 1:
        return n
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a
"""
    
    tools_code = llm.invoke(prompt).content
    
    # 注册到环境
    try:
        python_env.run(tools_code)
        status = "✅ 工具生成成功"
    except Exception as e:
        status = f"❌ 工具生成失败：{e}"
    
    return {
        **state,
        "generated_tools": tools_code,
        "messages": state["messages"] + [{
            "role": "system",
            "content": f"{status}\n\n生成的工具：\n```python\n{tools_code}\n```"
        }]
    }

def execute_with_tools(state: State) -> State:
    """使用生成的工具执行任务"""
    
    user_request = state["messages"][0]["content"]
    tools = state["generated_tools"]
    
    prompt = f"""
可用工具：
```python
{tools}
```

用户需求：{user_request}

使用上述工具完成任务。生成调用代码并执行。
要求：
1. 直接写调用代码
2. 使用 print() 输出结果
3. 不要解释，只要代码
"""
    
    execution_code = llm.invoke(prompt).content
    
    try:
        result = python_env.run(execution_code)
        response = f"✅ 执行成功\n\n结果：\n{result}"
    except Exception as e:
        response = f"❌ 执行失败：{e}"
    
    return {
        **state,
        "messages": state["messages"] + [{
            "role": "assistant",
            "content": response
        }]
    }

# 构建图
graph = StateGraph(State)
graph.add_node("generate", analyze_and_generate_tools)
graph.add_node("execute", execute_with_tools)

graph.set_entry_point("generate")
graph.add_edge("generate", "execute")
graph.add_edge("execute", END)

app = graph.compile()

# === 测试案例 ===

# 测试 1：简单计算
result = app.invoke({
    "messages": [{"role": "user", "content": "帮我计算斐波那契数列第 20 项"}],
    "generated_tools": ""
})

# 测试 2：复杂任务
result = app.invoke({
    "messages": [{"role": "user", "content": "生成 100 个随机数，找出所有质数，计算它们的平均值"}],
    "generated_tools": ""
})

# 测试 3：全新需求
result = app.invoke({
    "messages": [{"role": "user", "content": "把 'HELLO WORLD' 转成 Morse 码"}],
    "generated_tools": ""
})
```

### 15.10 为什么工具执行不用 LLM？

#### 核心区别：谁擅长什么

**LLM 的能力：**
- ✅ **输入：可以是一坨乱七八糟的东西**
  - "帮我算一下 23 加上 45"
  - "23+45等于多少"
  - "二十三和四十五加起来"
- ✅ **输出：整整齐齐的结构化 JSON**
  ```json
  {
    "name": "add",
    "args": {"a": 23, "b": 45}
  }
  ```

**Python 函数的要求：**
- ✅ **输入：必须整整齐齐！**
  ```python
  def multiply(a:int, b:int) -> int:
      return a * b
  ```
- 必须是 `multiply(2, 3)` ✅
- 不能是 `multiply("帮我算 2 乘以 3")` ❌

#### 分工

```
自然语言（乱） 
    ↓
  LLM（理解混乱）
    ↓
结构化 JSON（整齐）
    ↓
Python 提取参数（需要整齐的输入）
    ↓
调用函数（整齐 → 整齐）
```

**所以：**
- ✅ LLM：擅长处理"乱" → "整齐"
- ✅ Python：只能处理"整齐" → "整齐"
- ✅ LLM 先把"乱"整理好，Python 再接手机械操作

**这就是为什么 Tool 节点不需要 LLM，因为 LLM 已经把最难的部分（理解混乱）做完了！** 🎯✨

## 十六、对照 main.py：图怎么转、state 怎么长

前面各章讲的是：**模型产出 JSON，Python 执行函数。**  
这一章补上实践时真正卡住的一层：**LangGraph 用一张图把这些步骤串起来，用 `messages` 记住走过的路。**

手搭一遍 `StateGraph` 是为了在脑子里留下路径；看懂之后，`create_react_agent(model, tools)` 就是同一张图的预装配，不是另一种魔法。

### 16.1 图：节点是函数，边是跳转

```
START → llm_call →（有 tool_calls？）→ tool_node → llm_call → …
                              ↓ 没有
                             END
```

- **节点**：名字绑到函数。`add_node("llm_call", llm_call)` 是在说：走到这个站，跑这段 Python。
- **边**：名字连到名字。`add_edge("tool_node", "llm_call")` 不管函数体，只接线。
- 先登记节点再接线，是因为一个节点可以有多条出口（`llm_call` 既能去 `tool_node` 也能 `END`）。边上传的是字符串，字符串对不上就会找不到节点。

`StateGraph(MessageState)` 只是新建空图，并规定所有节点共用同一种 state。`compile()` 之后才能 `invoke`。

### 16.2 state：进节点是全集，出节点是补丁

`MessageState` 里真正要盯的是这一行：

```python
messages: Annotated[list[AnyMessage], operator.add]
```

意思：`messages` 是对话日志；节点 `return {"messages": [新消息]}` 时，框架用 `operator.add`（列表 `+`）接到旧列表后面。  
你在 `tool_node` 里看不到 `state["messages"] += ...`，合并发生在 `return` 之后，规则就是上面这行。

节点**读到的是整份 state**，**return 的是自己新产生的那一截**。`SystemMessage(...) + state["messages"]` 只给模型当输入，不进 return，所以系统提示不会进 state。

对 `"Add 3 and 4 ."`，`messages` 长这样：

```
0. invoke 入口          [HumanMessage]
1. 第一次 llm_call 后    [HumanMessage, AIMessage(tool_calls=add)]
2. tool_node 后         […, ToolMessage(7)]     ← ToolMessage 在这一步合进去
3. 第二次 llm_call 后    […, AIMessage("… is 7")]
```

`llm_calls` 只是教程里的计数器，循环不靠它。它和 `messages` 合并方式不一样，见下一节。

### 16.3 reducer：定义、作用、怎么看、怎么用

节点 `return` 的是补丁，不是新的整份 state。**旧值和新值怎么合成下一个 state，由 reducer 决定。** 它写在 schema 上，不写在 `llm_call` / `tool_node` 的返回值里，所以函数体里看不到 `+=`。

**定义：** reducer 是一个函数，签名可以想成 `(旧值, 节点刚 return 的新值) -> 合并后的值`。LangGraph 在节点返回之后、进入下一站之前调用它。

**在哪看：** 只看 `MessageState` 每个字段怎么标注。

```python
class MessageState(TypedDict):
    messages: Annotated[list[AnyMessage], operator.add]  # 第二格就是 reducer
    llm_calls: int                                       # 没有 Annotated → 没有 reducer
```

| 你看到的写法 | 有没有 reducer | 合并方式 |
|--------------|----------------|----------|
| `Annotated[类型, 某个函数]` | 有，就是那个函数 | 用该函数合旧值和新值 |
| 只有 `int` / `str` / `list` | 没有 | **覆盖**：return 多少就是多少 |
| 节点没 return 这个键 | （用不上） | 旧值不动 |

**作用：** 让每个节点只交「我改了什么」，对话历史这种日志不会被后一个节点整表替换掉。`messages` 用 `operator.add`，对两个 list 就是 `+`：

```python
# 框架内部等价于
state["messages"] = operator.add(
    [HumanMessage, AIMessage],   # 旧
    [ToolMessage],               # tool_node return 的
)
# → [HumanMessage, AIMessage, ToolMessage]
```

`llm_call` 的 `"messages": [那一条 AIMessage]` 同样走这条 `add`，**不是覆盖对话**。两个节点对 `messages` 都是追加。

**没有 reducer 的字段（`llm_calls: int`）：** 默认覆盖。要计数只能自己算出新总数再 return：

```python
"llm_calls": state.get("llm_calls", 0) + 1   # 交出完整新值，盖掉旧值
```

`tool_node` 不 return `llm_calls`，计数器保持原样。循环不靠这个字段；看不懂可忽略。

如果给计数器也挂上 reducer，就可以每次只交「要加的量」：

```python
llm_calls: Annotated[int, operator.add]
# llm_call 里 return {"llm_calls": 1} 即可，框架对 int 做 +
```

这是 schema 怎么声明的问题，不是「`llm_call` 覆盖、`tool_node` 累计」。**累计还是覆盖，看字段，不看函数。**

**用法（写节点时）：**

```python
# messages 有 add → return 只交新消息
return {"messages": [ToolMessage(...)]}

# 错：把旧历史再 return 一遍，add 会把对话翻倍
return {"messages": state["messages"] + [ToolMessage(...)]}

# 错：messages 若没写 operator.add，return [新消息] 会把用户那句盖掉
```

文档里还常见 `add_messages`（LangGraph 自带），也是放在 `Annotated` 第二格，比裸 `operator.add` 更适合消息列表（去重、按 id 合并等）。本示例用 `operator.add` 已经够说明「追加」这件事。

**别绕晕的一句：** reducer 不是 `result` 里面的东西，是 `MessageState` 里字段的合并规则。`return {"messages": result}` 只告诉框架「去改 `messages` 这个键」；怎么改，去查该键的 `Annotated`。

### 16.4 tool_node 四行：真正执行函数的地方

```python
for tool_call in state["messages"][-1].tool_calls:
    tool = tools_by_name[tool_call["name"]]
    observation = tool.invoke(tool_call["args"])
    result.append(ToolMessage(content=observation, tool_call_id=tool_call["id"]))
```

- `[-1]` 是最后一条 **AIMessage**（指令），不是用户那句。
- `for`：一轮可以有多次 `tool_calls`。
- `tools_by_name[name]`：按字符串取已注册工具。
- `invoke(args)`：内部 `**` 拆包，普通 Python。
- `tool_call_id` 必须和指令的 `id` 对上，下一轮模型才知道「这条 7」属于哪一次调用。

### 16.5 should_continue：普通 if，不必再问模型

```python
if last_message.tool_calls:
    return "tool_node"
return END
```

要不要调工具，第一次 `llm_call` 已经写在 `tool_calls` 里了。这里只是读标志位跳边，和「订单已支付就发货」一样。再丢给 LLM 问一遍又贵、又可能改口。

这和 15.10 是同一件事：LLM 把「乱」收成整齐字段，程序读字段即可。

`add_conditional_edges("llm_call", should_continue, ["tool_node", END])` 里最后那个列表**可以不写**——运行时认的是函数 `return` 的节点名。列表主要给画图用。`Literal["tool_node", END]` 也只是类型标注，图不会靠它接线。

这张图**本来就是环**。停靠模型不再吐 `tool_calls`。若模型一直调工具，会撞上 `recursion_limit`（默认约 25 步），不是边自己断了。

### 16.6 这种图最常见的错

1. `messages` 忘了 `operator.add`，return 一条新消息把历史盖掉；或挂了 `add` 却把**整份历史** return 回去，对话翻倍。
2. `add_node` 的名字和 `should_continue` 的 return 对不上。
3. 没看 `messages[-1]`，或那条根本不是带 `tool_calls` 的 `AIMessage`。
4. `ToolMessage` 漏了 `tool_call_id`。
5. 忘了 `bind_tools`，模型只在文本里说话，条件边永远走 `END`。

### 16.7 和 create_react_agent 的关系

```python
from langgraph.prebuilt import create_react_agent
agent = create_react_agent(model, tools)
```

内部仍是：调模型 → 有 `tool_calls` 就执行工具 → 再调模型。官方把 `should_continue` 收成了 `tools_condition`（有 `tool_calls` 去 `"tools"`，否则 `"__end__"`）。

手写 `main.py` 是把零件摊开；工厂函数是同一配方少打字。初学先走手搭，才会知道那一行在干什么。

LangChain 提供模型和 `@tool`；LangGraph 管循环、分支、state。Agent 必须能转圈，所以基础智能体写在图上，而不是单向链上。
